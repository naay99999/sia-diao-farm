# บันทึกสภาพต้น (Tree Observations) — Design

วันที่: 2026-10-21
สถานะ: รออนุมัติ
ลำดับในแผนรวม: 1 จาก 5 (1. สภาพต้น → 2. แผนงานที่กดเป็นบันทึก → 3. คลังปุ๋ย/ยา → 4. รวมค่าใช้จ่ายเข้าการดูแล → 5. เกรดผลผลิต) แต่ละข้อมีเอกสารออกแบบของตัวเอง

## Intent และเหตุผล

ผู้ใช้คือเจ้าของสวนและคนดูแลสวน (ทุเรียน ประมาณ 100 ต้นต่อสวน) ทั้งสองคนเห็นข้อมูลชุดเดียวกัน คนงานรายวันไม่ได้ใช้แอป ในแต่ละวันจะวางแผนงานไว้ก่อน แล้วสั่งงานคนงานเป็นวันๆ จากนั้นทำงานในสวนระหว่างวัน และเปิดแอปช่วงเย็นเพื่อบันทึกสิ่งที่ทำไป ที่ต้นไม้แต่ละต้นมี QR แปะไว้ สแกนแล้วจะเปิดหน้าของต้นนั้น

ในอนาคตจะใช้ AI ช่วยวิเคราะห์ ตอนนี้เป้าหมายคือ **เก็บข้อมูลที่มีโครงสร้างให้ได้มากที่สุด โดยไม่ทำให้การกรอกยุ่งยาก**

ตอนนี้ระบบบันทึกได้แค่ช่วงการรักษา (care record แบบ pesticide) แต่ยังไม่มีที่บันทึกว่า **เจออะไร** สิ่งที่เจอจะถูกเขียนไว้ในช่อง `notes` ซึ่งเป็นข้อความอิสระ และนำไปวิเคราะห์ต่อไม่ได้

ขั้นตอนจริงที่ผู้ใช้เล่า: เจอใบไหม้หรือไรแดง → พ่นยาเฉพาะต้นนั้น → กลับไปดูซ้ำประมาณ 7 วันให้หลัง → หายแล้ว หรือต้องรักษาต่อ

## Goals

1. บันทึก "สิ่งที่พบ" ของแต่ละต้นได้สองแบบ โดยใช้ฟอร์มเดียว
   - **ปัญหา** (โรค แมลง/ไร อาการผิดปกติ เช่น ใบไหม้ ไรแดง): เปิดเป็น "เรื่องที่ยังไม่จบ" ของต้นนั้น และต้องติดตามจนกว่าจะปิด
   - **ระยะการเติบโต** (ออกดอก ติดผล ผลดก ฯลฯ): บันทึกไว้เฉยๆ ไม่ต้องติดตาม
2. บันทึกได้รายต้น และเลือกได้หลายต้นในครั้งเดียว (กรณีหลายต้นเป็นโรคเดียวกัน) ผู้ใช้จะจดเฉพาะต้นที่เด่นหรือผิดปกติเท่านั้น ไม่ได้เดินจดครบทุกต้น
3. บันทึกได้จากสองทาง: สแกน QR แล้วเข้าหน้าต้น หรือเข้าจากหน้าสวน
4. กรอกเสร็จได้ใน 2–3 แตะ ช่องที่บังคับมีแค่ "เลือกสิ่งที่พบ" ส่วนความรุนแรง รูป และหมายเหตุไม่บังคับ
5. สิ่งที่พบเลือกจากรายการที่มีให้ และผู้ใช้เพิ่มรายการเองได้ เพื่อให้ข้อมูลเป็นค่าเดียวกันทุกครั้ง ไม่ใช่ข้อความอิสระ
6. แนบรูปได้ (หลายรูปต่อบันทึก) และเก็บไว้ที่ Cloudflare R2
7. การติดตามปัญหา
   - ตอนเปิดปัญหา ระบบตั้งวันดูซ้ำเป็น **วันที่พบ + 7 วัน** ไว้ให้ และผู้ใช้แก้วันได้
   - เมื่อบันทึกการดูแล (พ่นยา/ใส่ปุ๋ย/อื่นๆ) ให้ต้นที่มีปัญหาเปิดอยู่ ระบบจะเสนอให้ผูกการดูแลนั้นเข้ากับปัญหา **โดยเลือกไว้ให้แล้ว แต่ยกเลิกได้** เมื่อผูกแล้ว วันดูซ้ำจะเลื่อนเป็นวันที่ดูแล + 7 วัน
   - การดูซ้ำมีสองทางเลือก: "หายแล้ว" ซึ่งจะปิดเรื่อง หรือ "ยังไม่หาย" ซึ่งจะบันทึกต่อในเรื่องเดิม ใส่หมายเหตุหรือรูปได้ และตั้งวันดูซ้ำครั้งใหม่ (ค่าเริ่มต้นคือ +7 วัน)
8. รายการที่เห็นตอนเย็น (ในแอปเท่านั้น ไม่มีการส่งแจ้งเตือน): หน้าสวนแสดง
   - "ต้องดูซ้ำ" คือต้นที่ถึงวันดูซ้ำหรือเลยกำหนดแล้ว
   - "ปัญหาค้างอยู่" คือปัญหาที่ยังเปิดอยู่ทั้งหมด
9. หน้าต้น
   - บนสุดแสดงสถานะล่าสุด: ปัญหาที่ยังเปิดอยู่ (ถ้ามี) และระยะการเติบโตล่าสุด
   - ไทม์ไลน์เดิม (การดูแลและผลผลิต) แสดงสิ่งที่พบและการดูซ้ำรวมเข้าไปด้วย

## Non-goals (ไม่อยู่ในข้อนี้)

- การส่งแจ้งเตือน ทั้ง push, LINE และอีเมล
- AI วิเคราะห์รูปหรือแนะนำการรักษา ตอนนี้แค่เก็บข้อมูลไว้ให้พร้อมใช้
- บัญชีคนงาน และระบบสิทธิ์ผู้ใช้ ตอนนี้ orchard ยังไม่ผูกกับ user และให้คงไว้แบบนั้น
- แผนงาน, คลังปุ๋ย/ยา, การรวมค่าใช้จ่าย และเกรดผลผลิต ซึ่งเป็นข้อ 2–5 ที่จะออกแบบแยก
- ข้อมูลสภาพอากาศ

## Anti-goals (ถ้าเป็นแบบนี้ถือว่าล้มเหลว แม้ระบบจะทำงานได้)

- ฟอร์มบังคับกรอกหลายช่อง หรือต้องพิมพ์ยาว จนตอนเย็นผู้ใช้ไม่อยากบันทึก
- สิ่งที่พบถูกเก็บเป็นข้อความอิสระ จนรวมสถิติหรือส่งให้ AI ไม่ได้
- ปัญหาที่เปิดไว้ค้างอยู่ตลอดไปโดยไม่มีใครเห็น หรือรายการ "ต้องดูซ้ำ" รกจนผู้ใช้เลิกดู
- ผูกการดูแลเข้ากับปัญหาโดยที่ผู้ใช้ไม่รู้ตัวและแก้ไม่ได้

## Constraints

- Stack เดิม: Laravel 13, Inertia v3 + React 19, Tailwind v4, Wayfinder, Pest ใช้ convention ตามโค้ดที่มีอยู่ เช่น controller ใน `app/Http/Controllers/Farm`, Form Request ใน `app/Http/Requests/Farm`, enum มี `label()`, `Inertia::flash('toast', ...)` และ timeline ใน `TreeController::timeline()`
- ข้อความทั้งหมดที่ผู้ใช้เห็นเป็นภาษาไทย ส่วนชื่อในโค้ดเป็นภาษาอังกฤษ
- Mobile-first และต้องเป็นไปตาม `DESIGN.md` เพราะผู้ใช้เปิดจากมือถือหลังสแกน QR
- รูปเก็บที่ Cloudflare R2 ผ่าน Laravel filesystem (S3 driver) ผู้ใช้ **อนุมัติแล้ว** ให้เพิ่ม `league/flysystem-aws-s3-v3` และมี bucket แล้ว ให้ตั้งค่า disk `r2` ผ่าน env ส่วนตอนพัฒนาและตอนเทสต์ให้ใช้ disk local หรือ `Storage::fake()`
- ต้องเขียน feature test ทุกส่วนที่เปลี่ยน

## ให้ผู้สร้างตัดสินใจเอง

- Schema และชื่อตาราง เช่น แยกตาราง observation, issue และ follow-up หรือรวมกัน รวมถึงวิธีเก็บรายการสิ่งที่พบ (enum + ตารางที่ผู้ใช้เพิ่มเอง หรือตารางเดียวที่มี seed) โดยต้องตอบโจทย์ข้อ 5 และคิวรีสถิติง่าย
- ถ้าเลือกหลายต้น จะเปิดปัญหาแยกรายต้นหรือเปิดร่วมกัน ขอให้การดูซ้ำและการปิดเรื่องทำได้รายต้น เพราะแต่ละต้นอาจหายไม่พร้อมกัน
- รายการสิ่งที่พบเริ่มต้นสำหรับทุเรียน เช่น ไรแดง เพลี้ยไฟ เพลี้ยไก่แจ้ง หนอนเจาะผล ใบไหม้ ไฟทอปธอร่า/รากเน่าโคนเน่า ราสีชมพู ใบติด และระยะ เช่น แตกใบอ่อน ออกดอก ดอกบาน ติดผล ผลดก ผลร่วง
- การย่อขนาดรูปก่อนอัปโหลด จำนวนรูปสูงสุด และขนาดไฟล์สูงสุด
- Layout และ UI ต้องเป็นไปตาม DESIGN.md และ component ที่มีอยู่ เช่น `care-record-form.tsx`, `section-tabs.tsx`
- ต้นที่ถูก remove (`removed_on`) แล้วยังมีปัญหาเปิดอยู่ ควรไม่แสดงในรายการ "ต้องดูซ้ำ"
