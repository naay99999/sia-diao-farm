# ออกแบบใหม่: ติดตามรายต้นด้วย QR + ตัดส่วนที่เกินจำเป็น

วันที่: 2026-10-21
แทนที่: `2026-06-27-farm-erp-data-model-design.md` (โมเดล แปลง → รอบการปลูก → เกรด)

## เจตนา (ทำไม)

ระบบเดิมออกแบบเป็น ERP ทั่วไป: หลายชนิดผลไม้ หลายพันธุ์ เกรด แปลง รอบการปลูกที่มี stage/status ละเอียด และ role ผู้ใช้ แต่ความจริงคือ

- สวนปลูก **ทุเรียนอย่างเดียว**
- ผู้ใช้จริงมี **คนเดียว คือเจ้าของสวน** คนงานไม่ใช้ระบบ
- มี **หลายสวน หลายที่** แต่ละสวนไม่ใหญ่
- เจ้าของอยากรู้ข้อมูล **รายต้น** — ติด QR ที่ต้น สแกนแล้วเห็นประวัติต้นนั้นและบันทึกได้ทันที
- งานจริงส่วนใหญ่ทำ **ทั้งสวนพร้อมกัน** (ใส่ปุ๋ยทั้งสวน) จึงต้องบันทึกหลายต้นในครั้งเดียวได้

ระบบใหม่จึงเปลี่ยนแกนจาก "แปลง" เป็น "สวน → ต้น" และตัดทุกอย่างที่ไม่ได้ใช้

## เป้าหมาย

1. ทุกต้นมี QR — สแกนแล้วเปิดหน้าต้นนั้น (ต้องล็อกอิน) เห็นประวัติล่าสุด และมีปุ่มบันทึก ใส่ปุ๋ย / ฉีดยา / ผลผลิต
2. บันทึกการดูแล (ปุ๋ย ยา) ได้ทั้งรายต้นและหลายต้นพร้อมกัน — ค่าเริ่มต้นเลือกทั้งสวน แล้วติ๊กออกบางต้นได้
3. บันทึกผลผลิตรายต้น (กิโล, จำนวนลูกไม่บังคับ) ทั้งผ่าน QR และแบบตารางทั้งสวนในหน้าเดียว
4. แต่ละสวนมี **รอบฤดู** ของตัวเอง (คร่อมปีได้ แต่ละสวนเวลาไม่ตรงกัน) ดูสรุปผลผลิต/รายได้ต่อรอบได้
5. บันทึกการขายระดับสวน/รอบ (น้ำหนักรวม + ยอดเงิน)
6. บันทึกค่าใช้จ่าย ดูยอดรวม — ผูกกับรอบฤดูของสวนได้แบบไม่บังคับ
7. พิมพ์ QR ของทั้งสวนเป็นแผ่นเพื่อติดต้น
8. โค้ดเล็กลง — ลบทุกอย่างที่ไม่อยู่ในรายการข้างบน

## ไม่ทำ (non-goals)

- เกรดผลไม้ (ยังไม่เคยขายจริง ไม่รู้ว่าผู้ซื้อแบ่งเกรดอย่างไร — เพิ่มทีหลังได้)
- หลายชนิดผลไม้ / ตาราง master ของพันธุ์
- การกระจายต้นทุนลงรายสวน/รายต้น (ปุ๋ยซื้อล็อตเดียวใช้หลายสวน — ดูต้นทุนรวมไปก่อน)
- ราคาในบันทึกใส่ปุ๋ย/ยา (ค่าใช้จ่ายบันทึกแยก)
- หลายผู้ใช้, role, สิทธิ์
- QR ที่เปิดดูได้โดยไม่ล็อกอิน
- ใช้งาน offline

## Anti-goals (ถ้าเป็นแบบนี้ถือว่าล้มเหลว แม้จะทำงานได้)

- ยืนที่ต้นแล้วต้องกดหลายชั้นกว่าจะบันทึกได้ — หน้าต้นต้องบันทึกได้ในไม่กี่แตะบนมือถือ
- ใส่ปุ๋ยทั้งสวนแล้วต้องบันทึกทีละต้น
- มีเมนูตั้งค่า master data ให้ต้องไปกรอกก่อนเริ่มใช้งาน
- หน้าจอออกแบบมาสำหรับเดสก์ท็อป — หน้าที่ใช้ในสวนต้องใช้บนมือถือได้ดีก่อน

## ข้อจำกัด

- เริ่มฐานข้อมูลใหม่ทั้งหมด **ไม่ต้อง migrate ข้อมูลเดิม** — แก้/ลบ migration เดิมได้ตรง ๆ
- ยึด stack เดิม: Laravel 13, Inertia v3 + React 19, Tailwind v4, Wayfinder, Fortify, Pest, SQLite
- UI ภาษาไทยเท่านั้น (ตาม CLAUDE.md) ปีแสดงเป็น พ.ศ. เหมือนระบบเดิม
- การเพิ่ม dependency ต้องได้รับอนุมัติก่อน (ดู "เรื่องที่รอเจ้าของตัดสินใจ")

## โมเดลข้อมูล

```
orchards        สวน
  id, name, location (nullable, ข้อความ), notes (nullable), timestamps

trees           ต้นทุเรียน
  id, orchard_id, code (เช่น "A-012" — unique ภายในสวน, แสดงบนป้าย QR),
  variety (nullable, ข้อความอิสระ เช่น หมอนทอง), planted_on (nullable),
  notes (nullable), timestamps

seasons         รอบฤดูของสวน
  id, orchard_id, name (เช่น "ฤดู 2569"), started_on, ended_on (nullable = รอบปัจจุบัน),
  notes (nullable), timestamps
  กติกา: สวนหนึ่งมีรอบที่ยังไม่ปิดได้ไม่เกิน 1 รอบ

care_records    บันทึกการดูแล (หนึ่งครั้งที่ทำ อาจครอบหลายต้น)
  id, orchard_id, season_id (nullable), type (enum: fertilizer ใส่ปุ๋ย / pesticide ฉีดยา / other อื่น ๆ),
  performed_on, product (nullable — ชื่อปุ๋ย/ยา), quantity (nullable — ข้อความอิสระ เช่น "1 กก./ต้น"),
  notes (nullable), timestamps

care_record_tree  pivot: care_record_id, tree_id

harvests        ผลผลิตรายต้น
  id, tree_id, season_id (nullable), harvested_on, weight_kg, fruit_count (nullable),
  notes (nullable), timestamps

sales           การขาย (ระดับสวน/รอบ)
  id, orchard_id, season_id (nullable), sold_on, buyer_name (nullable),
  weight_kg, amount (ยอดเงินรวม), notes (nullable), timestamps

expenses        ค่าใช้จ่าย
  id, season_id (nullable — ผูกกับรอบของสวนใดสวนหนึ่งถ้าเป็นค่าใช้จ่ายเฉพาะสวน),
  category (enum), spent_on, amount, notes (nullable), timestamps
```

**การผูกรอบฤดู (การตัดสินใจของผู้ออกแบบ):** care_records / harvests / sales **ไม่เก็บ `season_id`** — คำนวณรอบตอน query จากวันที่ของบันทึกเทียบกับช่วง `started_on`–`ended_on` ของรอบในสวนนั้น (`ended_on` null = ถึงวันนี้) ข้อดีคือสร้างรอบย้อนหลัง แก้วันรอบ หรือแก้วันที่บันทึกแล้ว ตัวเลขสรุปยังถูกต้องเสมอโดยไม่ต้อง re-sync ผู้ใช้ไม่ต้องเลือกรอบในฟอร์มเหล่านี้ ให้ลบ `season_id` ออกจากตารางทั้งสามในโมเดลข้างบน
กติกาเพิ่ม: รอบฤดูในสวนเดียวกัน **ห้ามช่วงวันซ้อนกัน** (validate ตอนสร้าง/แก้รอบ) เพื่อให้วันหนึ่งตรงกับรอบเดียวเท่านั้น
ค่าใช้จ่ายยังเก็บ `season_id` (nullable) เพราะไม่ได้ผูกกับสวนผ่านทางอื่น และผู้ใช้เลือกเองว่าจะผูกหรือไม่

**หมวดค่าใช้จ่าย:** enum ตายตัว ไม่มีหน้าจัดการหมวด — ปุ๋ย, ยา/สารเคมี, ค่าแรง, น้ำ/ไฟ/น้ำมัน, อุปกรณ์, อื่น ๆ *(การตัดสินใจของผู้ออกแบบ)*

**ตัดคอลัมน์ `recorded_by`** ทุกตาราง — มีผู้ใช้คนเดียว

## หน้าจอ

| หน้า | เนื้อหา |
|---|---|
| **สวนทั้งหมด** (หน้าแรกหลังล็อกอิน แทนแดชบอร์ด) | การ์ดรายสวน: ชื่อ, จำนวนต้น, รอบปัจจุบัน, ผลผลิตรวมของรอบปัจจุบัน; ปุ่มเพิ่มสวน |
| **สวน** | รายการต้น (code, พันธุ์, ผลผลิตรอบนี้), ปุ่ม: เพิ่มต้น / เพิ่มหลายต้น, บันทึกการดูแลหลายต้น, บันทึกผลผลิตแบบตาราง, พิมพ์ QR; ส่วนรอบฤดู (เริ่ม/ปิดรอบ, ลิงก์ดูรอบเก่า); ประวัติการดูแลของสวน; การขาย |
| **ต้น** (ปลายทาง QR) | หัว: code + ชื่อสวน + พันธุ์; ปุ่มใหญ่ 3 ปุ่ม: ใส่ปุ๋ย / ฉีดยา / ผลผลิต (เปิดฟอร์มสั้น ๆ วันที่ default วันนี้); ไทม์ไลน์ประวัติรวม (การดูแล + ผลผลิต) เรียงล่าสุดก่อน; ผลผลิตสรุปต่อรอบ |
| **บันทึกการดูแลหลายต้น** | เลือกชนิด, วันที่, ชื่อสินค้า, ปริมาณ, หมายเหตุ; รายชื่อต้นทั้งสวนติ๊กไว้ทั้งหมด มี "เลือกทั้งหมด/ไม่เลือก" ติ๊กออกได้ |
| **บันทึกผลผลิตแบบตาราง** | วันที่ 1 ช่อง + ตารางทุกต้นในสวน แต่ละแถวมีช่อง กก. และจำนวนลูก — บันทึกเฉพาะแถวที่กรอก |
| **รอบฤดู** | สรุป: ผลผลิตรวม, ผลผลิตรายต้น (เรียงมากไปน้อย), ยอดขาย, ค่าใช้จ่ายที่ผูกกับรอบนี้ |
| **ค่าใช้จ่าย** | รายการ + ฟอร์มเพิ่ม (รอบฤดูเลือกได้ไม่บังคับ) + ยอดรวม และยอดรวมแยกหมวด, กรองตามช่วงวันที่ |
| **พิมพ์ QR** | หน้าเหมาะกับการพิมพ์: ตารางป้าย แต่ละป้ายมี QR + code ต้น + ชื่อสวน; ใช้ print CSS |
| **ตั้งค่า** | โปรไฟล์ (ชื่อ, อีเมล) + เปลี่ยนรหัสผ่าน — หน้าเดียวพอ |

เมนูหลัก: สวน, ค่าใช้จ่าย (และตั้งค่าในเมนูผู้ใช้)

แก้ไข/ลบ: ทุกบันทึก (การดูแล, ผลผลิต, ขาย, ค่าใช้จ่าย, ต้น, สวน, รอบ) ต้องแก้ไขและลบได้ — บันทึกผิดเป็นเรื่องปกติเวลากรอกในสวน ลบสวน/ต้นต้องยืนยันก่อน

**URL ใน QR:** ใช้ URL สั้นที่ไม่ผูกกับ code (code อาจเปลี่ยน) เช่น `/t/{tree id}` ที่ redirect ไปหน้าต้น — ป้ายที่ติดไปแล้วต้องไม่เสียเมื่อแก้ชื่อหรือ code ต้น ถ้ายังไม่ล็อกอิน ให้ล็อกอินแล้วกลับมาที่หน้าต้นเดิม (intended redirect)

## ที่เหลือให้ผู้สร้างตัดสิน

- รูปแบบการตั้ง code ต้น และ UX "เพิ่มหลายต้น" (เช่น prefix + เลขเริ่ม + จำนวน)
- เลย์เอาต์ป้าย QR (ขนาด, จำนวนต่อแผ่น A4)
- โครงสร้าง controller/route, ชื่อคลาส, การแบ่ง component — ตาม convention ของโปรเจกต์
- Seeder: สร้างผู้ใช้เจ้าของสวน 1 คน (+ ข้อมูลตัวอย่างสำหรับ dev ถ้าเป็นประโยชน์)
- รายละเอียด validation (เช่น `ended_on >= started_on`, `weight_kg > 0`)
- เขียน test ใหม่ให้ครอบโมเดล/controller ใหม่ ลบ test ของสิ่งที่ถูกลบ

## เรื่องที่รอเจ้าของตัดสินใจ

- **ต้นตาย/ถูกโค่น** — เก็บประวัติไว้ (อนุมัติตามข้อเสนอ): `trees` มีคอลัมน์ `removed_on` (nullable) ต้นที่มีค่านี้จะถูกซ่อนจากรายการต้น ตารางกรอกผลผลิต ฟอร์มการดูแลหลายต้น และหน้าพิมพ์ QR แต่ยังนับในสรุปรอบฤดูเดิม และหน้าต้นยังเปิดดูได้ (มีป้าย "ไม่อยู่แล้ว") ในหน้าสวนมีตัวเลือกให้แสดงต้นที่ไม่อยู่แล้ว การลบจริงทำได้เฉพาะต้นที่ยังไม่มีบันทึกใดเลย (ไว้แก้กรณีเพิ่มต้นผิด)

## การตัดสินใจของผู้ออกแบบ (ให้เจ้าของตรวจ)

- **QR:** สร้างฝั่ง server ด้วย `bacon/bacon-qr-code` (v3 ติดตั้งอยู่แล้วเพราะ Fortify ใช้) แล้วส่ง SVG เป็น prop ให้หน้าพิมพ์ — เพิ่มชื่อใน `composer.json` ให้ชัดเจนแทนการอาศัย Fortify ไม่มีการติดตั้งแพ็กเกจใหม่
