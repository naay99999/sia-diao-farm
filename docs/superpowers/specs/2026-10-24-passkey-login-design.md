# ล็อกอินด้วย passkey

วันที่: 2026-10-24

## เจตนาและเหตุผล

เจ้าของเป็นคนตั้งค่าให้สมาชิกแต่ละคน**บนมือถือของสมาชิกเอง**ในครั้งเดียว คือ เปิดเว็บ → ล็อกอิน → ติดตั้งเป็น PWA → เชื่อม Claude ผ่าน MCP หลังจากนั้นสมาชิกใช้ Claude เป็นหลัก ส่วนเว็บเปิดแค่เพื่อดู เช่น สแกน QR ต้นไม้เพื่อดูรายละเอียด

session แบบ "จดจำฉัน" ทำให้แทบไม่ต้องล็อกอินซ้ำ แต่เมื่อ session หลุด (หรือการเชื่อม Claude ผ่าน OAuth พาไปหน้าล็อกอิน) สมาชิกต้องกรอกอีเมลและรหัสผ่าน ซึ่งเขาจำไม่ได้หรือพิมพ์ลำบากบนมือถือ เป้าหมายคือให้ล็อกอินใหม่ได้แค่สแกนนิ้วหรือใบหน้า

## เป้าหมาย

- หน้าล็อกอินเน้นปุ่ม "เข้าสู่ระบบด้วย passkey" ไว้บนสุด กดแล้วสแกนนิ้ว/ใบหน้าได้เลย ไม่ต้องพิมพ์อีเมล
- ล็อกอินด้วย passkey แล้วจำ session เสมอ (remember) เหมือนติ๊ก "จดจำฉัน"
- หลังล็อกอินด้วยรหัสผ่าน ถ้าบัญชีนั้นยังไม่มี passkey เลย ให้ชวนเพิ่ม passkey ทันที (ปุ่ม "เพิ่มเลย" / "ไว้ทีหลัง")
- หน้าโปรไฟล์มีส่วน "Passkey": แสดงรายการ (ชื่อ, วันที่เพิ่ม, ใช้ล่าสุด) เพิ่มและลบได้
- หน้าสมาชิก (เจ้าของ) แสดงป้ายว่าสมาชิกแต่ละคนมี passkey แล้วหรือยัง
- บัญชีที่ถูกปิดใช้งาน**ต้องล็อกอินด้วย passkey ไม่ได้** และเห็นข้อความเดิม "บัญชีนี้ถูกปิดใช้งานแล้ว"

## Non-goals

- ตัดรหัสผ่านออก — ทุกคนยังมีรหัสผ่าน และเจ้าของยังตั้งรหัสใหม่ให้สมาชิกได้จากหน้าสมาชิกเหมือนเดิม
- เจ้าของเพิ่มหรือลบ passkey แทนสมาชิกจากหน้าสมาชิก (เจ้าของตั้งค่าบนเครื่องของสมาชิกโดยล็อกอินเป็นสมาชิกคนนั้นอยู่แล้ว)
- ใช้ passkey ยืนยันตัวตนซ้ำก่อนทำรายการสำคัญ (`/passkeys/confirm`)
- ลิงก์ล็อกอิน, magic link, LINE/Google login, OTP, 2FA
- สมัครสมาชิกเอง / ส่งอีเมล

## Anti-goals (ถ้าเป็นแบบนี้ถือว่าพัง แม้จะใช้งานได้)

- บัญชีที่ปิดใช้งานแล้วยังเข้าได้ทาง passkey
- ล็อกอินด้วยรหัสผ่านแบบเดิมพังหรือยากขึ้น
- กล่องชวนเพิ่ม passkey โผล่ซ้ำทุกครั้งที่เปิดหน้า จนน่ารำคาญ

## ข้อจำกัด

- ใช้ระบบ passkey ที่มากับ Fortify v1.37.2 (`Features::passkeys()` ซึ่งใช้ `laravel/passkeys` ^0.2 ที่ติดตั้งมาด้วยแล้ว) **ไม่เพิ่ม package ฝั่ง PHP**
- ฝั่งหน้าเว็บใช้ npm `@laravel/passkeys` ตามที่ Fortify แนะนำ — เป็น dependency ใหม่ ผู้ใช้อนุมัติแนวทางนี้แล้ว (ยืนยันอีกครั้งตอนติดตั้ง)
- passkey ผูกกับโดเมนของ `APP_URL` และต้องใช้ HTTPS (ยกเว้น `localhost`)
- PWA บน iPhone เก็บ cookie แยกจาก Safari จึงต้องล็อกอินและเพิ่ม passkey จาก**ในตัว PWA** ตอนตั้งค่า (passkey ใช้ข้ามกันได้ แต่ session ไม่ข้าม) — ไม่ต้องเขียนโค้ดเพิ่ม แต่เป็นขั้นตอนที่เจ้าของต้องรู้
- ข้อความทั้งหมดเป็นภาษาไทย รวมถึง `aria-label`
- ตามกติกาโปรเจกต์: ทุกการเปลี่ยนแปลงต้องมี test (Pest), รัน Pint

## สิ่งที่ตัดสินใจแล้ว

### Backend

- เปิด `Features::passkeys(['confirmPassword' => false])` ใน `config/fortify.php` — **ไม่ต้องกรอกรหัสผ่านซ้ำ**ก่อนเพิ่ม/ลบ passkey (เจ้าของเพิ่งล็อกอินให้สมาชิก ขั้นนี้ไม่มีประโยชน์) *(การตัดสินใจของ Claude ที่ผู้ใช้รับทราบแล้ว)*
- `User` ใช้ trait `Laravel\Fortify\PasskeyAuthenticatable` และ implement `Laravel\Fortify\Contracts\PasskeyUser`
- publish migration ตาราง `passkeys` (คอลัมน์: `user_id`, `name`, `credential_id`, `credential`, `last_used_at`, timestamps — cascade เมื่อลบ user)
- กันบัญชีปิดใช้งานด้วย `Passkeys::authorizeLoginUsing()` ใน `FortifyServiceProvider` ให้ผลลัพธ์และข้อความเหมือนการล็อกอินด้วยรหัสผ่าน ("บัญชีนี้ถูกปิดใช้งานแล้ว") — callback คืนได้แค่ true/false และถ้าคืน false จะได้ข้อความภาษาอังกฤษของ library จึงต้อง throw `ValidationException` ในตัว callback แบบเดียวกับ `authenticateUsing`
- `/passkeys/login` ตอบเป็น JSON พร้อม URL `intended` หน้าเว็บต้องไปยัง URL นั้นแบบโหลดหน้าเต็ม (`window.location`) ไม่ใช่ Inertia visit เพื่อให้กลับเข้า flow OAuth ของ Claude (`/oauth/authorize`) ได้ถูกต้อง
- ล็อกอินด้วย passkey ต้องจำ session เสมอ — `PasskeyLoginController` ใช้ `$request->remember()` ดังนั้นฝั่งหน้าเว็บส่ง `remember: true` ทุกครั้ง (หรือบังคับฝั่ง server ก็ได้ — ให้ builder เลือก แต่ผลต้องเป็น remember เสมอ)
- ส่งข้อมูลให้หน้าเว็บ:
  - หน้าโปรไฟล์: รายการ passkey ของผู้ใช้ (`id`, `name`, `created_at`, `last_used_at`)
  - หน้าสมาชิก: `hasPasskey` (bool) ต่อสมาชิกแต่ละคน
  - สัญญาณสำหรับกล่องชวนเพิ่ม passkey (ดูด้านล่าง)

### หน้าล็อกอิน (`resources/js/pages/auth/login.tsx`)

- ปุ่มหลักขนาดเต็มความกว้าง "เข้าสู่ระบบด้วย passkey" อยู่บนสุด
- ใต้ปุ่มเป็นเส้นคั่น "หรือใช้รหัสผ่าน" แล้วตามด้วยฟอร์มอีเมล/รหัสผ่าน/จดจำฉันแบบเดิม (ไม่ซ่อนหลังลิงก์ แค่วางเป็นลำดับรอง)
- ถ้า browser ไม่รองรับ passkey ให้ซ่อนปุ่ม passkey
- ผู้ใช้กดยกเลิกหน้าต่างสแกน → ไม่ต้องแสดง error ใหญ่ อยู่หน้าเดิม
- passkey ไม่ถูกต้อง / บัญชีปิดใช้งาน → แสดงข้อความภาษาไทยใต้ปุ่ม
- ข้อความอธิบายใต้หัวเรื่อง (`Login.layout.description`) ปรับให้พูดถึง passkey ด้วย

### กล่องชวนเพิ่ม passkey

- แสดง**เฉพาะหลังล็อกอินด้วยรหัสผ่านสำเร็จ** และบัญชีนั้นยังไม่มี passkey เลย — แสดงครั้งเดียวต่อการล็อกอินนั้น (เช่น flag ใน session ที่ตั้งตอนล็อกอินและล้างเมื่อแสดงหรือกดปิด) *(การตัดสินใจของ Claude)*
- ข้อความ: "เพิ่ม passkey เพื่อเข้าสู่ระบบครั้งหน้าด้วยการสแกนนิ้วหรือใบหน้า" ปุ่ม "เพิ่มเลย" และ "ไว้ทีหลัง"
- "เพิ่มเลย" → สร้าง passkey ทันทีในกล่องนั้น สำเร็จแล้วแจ้งผลและปิดกล่อง
- ถ้า browser ไม่รองรับ passkey ไม่ต้องแสดงกล่อง
- **ไม่ชวนในเส้นทาง OAuth ของ Claude** — หน้าอนุญาต (`mcp.authorize`) เป็น Blade view ไม่ต้องแก้ ถ้าล็อกอินด้วยรหัสผ่านระหว่าง OAuth กล่องจะขึ้นเมื่อเปิดหน้าแอปปกติในครั้งถัดไป (หรือไม่ขึ้นเลยถ้าไม่เปิด) ซึ่งรับได้ เพราะเจ้าของเพิ่ม passkey ให้ทุกคนตอนตั้งค่าครั้งแรกอยู่แล้ว *(ผู้ใช้ตัดสินใจ)*
- แสดงที่หน้าแรกหลังล็อกอิน (`/orchards` ตาม `fortify.home`) หรือใน layout หลัก — ให้ builder เลือก ขอแค่เห็นทันทีหลังล็อกอิน

### หน้าโปรไฟล์ (`resources/js/pages/settings/profile.tsx`)

- ส่วนใหม่ "Passkey" ใต้ส่วนข้อมูลโปรไฟล์
- รายการ passkey: ชื่อ, เพิ่มเมื่อ, ใช้ล่าสุด (วันที่แบบไทย) และปุ่มลบ (มีการยืนยันก่อนลบ)
- ปุ่ม "เพิ่ม passkey" — ตั้งชื่อ passkey ให้อัตโนมัติจากอุปกรณ์/browser (เช่น "iPhone · Safari") ไม่ต้องให้ผู้ใช้พิมพ์ *(การตัดสินใจของ Claude)*
- ไม่มี passkey → ข้อความว่างสั้น ๆ ชวนให้เพิ่ม

### หน้าสมาชิก (`resources/js/pages/settings/members.tsx`)

- ป้ายเล็กต่อสมาชิก: "มี passkey" หรือ "ยังไม่มี passkey" ดูอย่างเดียว ไม่มีปุ่มจัดการ

## Tests ที่ต้องมี

- ล็อกอินด้วยรหัสผ่านยังทำงานเหมือนเดิม (test เดิมต้องผ่าน)
- บัญชีที่ปิดใช้งานล็อกอินด้วย passkey ไม่ได้
- route passkey ลงทะเบียนครบและเพิ่ม/ลบได้โดยไม่ต้องยืนยันรหัสผ่าน; ลบ passkey ของคนอื่นไม่ได้
- หน้าโปรไฟล์ส่งรายการ passkey ของผู้ใช้ตัวเองเท่านั้น
- หน้าสมาชิกส่ง `hasPasskey` ถูกต้อง
- สัญญาณกล่องชวนเพิ่ม passkey: มีหลังล็อกอินด้วยรหัสผ่านเมื่อยังไม่มี passkey, ไม่มีเมื่อมี passkey แล้ว, ไม่โผล่ซ้ำ

(การตรวจลายเซ็น WebAuthn จริงทดสอบด้วย Pest ไม่ได้ง่าย — ทดสอบที่ขอบเขตของแอปเรา เช่น callback `authorizeLoginUsing` และ props ก็พอ)

## สิ่งที่ปล่อยให้ builder ตัดสินใจ

- รายละเอียดการเรียก `@laravel/passkeys` และการต่อกับ Wayfinder routes
- จะบังคับ remember ฝั่ง server หรือส่งจากหน้าเว็บ
- ตำแหน่งที่แน่นอนของกล่องชวนเพิ่ม passkey และ component ที่ใช้ (ใช้ของที่มีใน `resources/js/components` ก่อน)
- วิธีสร้างชื่ออุปกรณ์อัตโนมัติ
